A boosted product search engine, built line by line in Rust

We'll turn a folder full of H&M product listings into something you can query in plain English — "summer dress for a wedding" — and get back ranked results that account for more than just meaning. Along the way you'll write a small embedding wrapper, a Qdrant client, and a retrieval-augmented generation (RAG) layer that hands the results to a local LLM.

1 The idea, before the code

Two ingredients make this project work, and it's worth separating them before you write a single line of Rust.

Semantic search. Instead of matching keywords, we turn both the products and the search query into vectors — long lists of numbers that capture meaning — using an embedding model. Products with a similar meaning to the query end up with vectors that point in a similar direction. Qdrant is the database that stores those vectors and finds the closest matches.

Boosting. The closest match by meaning isn't always the best result to show a shopper. A dress nobody buys, or one that's about to be discontinued, probably shouldn't outrank a near-identical, popular, recently-added one. So after Qdrant finds semantically close products, we nudge the ranking using two extra numbers already stored alongside each product: popularity and recency.

The formula is simple addition:

the boosting formula
boosted_score = semantic_similarity
              + popularity_weight * popularity
              + recency_weight   * recency

Everything we build from here is really just: embed the query → ask Qdrant to apply that formula → hand the top results to an LLM so it can answer in a sentence instead of a table.

why anyhow?

Rust normally forces every function to name its exact error type. anyhow::Result<T> is a shortcut for application code (as opposed to library code): it lets you use ? to bubble up errors from Qdrant, fastembed, and Ollama alike without writing a custom error enum that wraps all three. You'll see Result<T> everywhere in this project — that's anyhow::Result, imported once at the top of each file.

serde, unused (so far)

serde and serde_json are in the dependency list but nothing we've written yet calls into them directly — Qdrant's client uses them internally to (de)serialize payload values, and they're handy to have on hand if you later want to serialize a Product to JSON yourself, e.g. for an HTTP API on top of this CLI.

3 Turning text into vectors

This file has exactly one job: load an embedding model once, and use it to turn a string into a vector of numbers. We reach for fastembed, which ships a model called BGE-small-en-v1.5 — small enough to run on a laptop CPU, and, conveniently, the same model whose vectors are already sitting in the Qdrant collection we're querying against. Both sides need to speak the same "language" of numbers, or the distances between vectors are meaningless.

The struct and constructor

src/embedder.rs
use anyhow::Result;
use fastembed::{EmbeddingModel, InitOptions, TextEmbedding};

pub struct Embedder {
    model: TextEmbedding,
}

impl Embedder {
    /// Downloads (first run only, cached after) and loads the model.
    pub fn new() -> Result<Self> {
        let model = TextEmbedding::try_new(
            InitOptions::new(EmbeddingModel::BGESmallENV15)
                .with_show_download_progress(true),
        )?;

        Ok(Self { model })
    }
}

Nothing unusual yet: a struct that owns the loaded model, and a constructor that downloads and initializes it. Loading a model is the slow part, so we only do it once, in main, and reuse the same Embedder for every query.

Embedding a query

src/embedder.rs (continued)
    /// Embed a single query string.
    pub fn embed_query(&self, text: &str) -> Result<Vec<f32>> {
        let mut embeddings = self.model.embed(vec![text.to_string()], None)?;
        Ok(embeddings.remove(0))
    }
}

The embed() method is built for batches — you hand it a Vec of strings and get back a Vec of vectors, one per input, so it can process many pieces of text efficiently in one pass. We only ever want to embed one query at a time here, so we wrap our single string in a one-element vec![...], and then need to pull that single result back out.

rust concept — Vec::remove

embeddings.remove(0) takes ownership of the element at index 0 and returns it, shifting every element after it one slot to the left to close the gap. That shifting is what makes remove an O(n) operation on a Vec — fine here, since our vector only ever has one element, but worth remembering before you reach for remove(0) in a hot loop over a large collection.

It's easy to confuse with two lookalikes: indexing with embeddings[0] only borrows the element (and panics if you then try to also own it while the vector exists), and .pop() only ever removes the last element. remove is the one that lets you take ownership of a value from the middle — or, as here, from the front — of a Vec.

We now have a way to turn any string into a 384-number vector. Next: a place to send that vector.

4 Querying Qdrant and applying the boost

This is the biggest file in the project, so we'll build it in layers: first a plain semantic search, then the boosted version, then the Product type we'll hand back to the rest of the program.

Connecting

src/qdrant_store.rs
use anyhow::Result;
use qdrant_client::Qdrant;
use qdrant_client::qdrant::{QueryPointsBuilder, PrefetchQueryBuilder,
    FormulaBuilder, Expression, ScoredPoint, point_id::PointIdOptions, value::Kind};

pub const COLLECTION_NAME: &str = "hm_products";
const DENSE_VECTOR: &str = "dense";
const PREFETCH_LIMIT: u64 = 100;

pub struct Store {
    client: Qdrant,
}

impl Store {
    pub fn connect(url: &str) -> Result<Self> {
        let client = Qdrant::from_url(url).build()?;
        Ok(Self { client })
    }
}

Qdrant's Rust client talks gRPC, which by default listens on port 6334 — not the 6333 REST port you'd use from Python or curl. Easy to trip over the first time.

A plain semantic search

src/qdrant_store.rs (inside impl Store)
    pub async fn semantic_search(&self, query_vector: Vec<f32>, limit: u64)
        -> Result<Vec<ScoredPoint>>
    {
        let response = self.client
            .query(
                QueryPointsBuilder::new(COLLECTION_NAME)
                    .query(query_vector)
                    .using(DENSE_VECTOR)
                    .limit(limit)
                    .with_payload(true),
            )
            .await?;

        Ok(response.result)
    }

This alone gives you ordinary meaning-based search: find the vectors nearest to the query vector. It's also the baseline we'll compare the boosted results against later.

Boosting: prefetch, then re-rank with a formula

Qdrant's formula query lets you fetch a wide pool of semantic candidates and then re-score them server-side using payload fields — no need to pull everything back to Rust and re-sort it by hand.

src/qdrant_store.rs (inside impl Store)
    pub async fn boosted_search(
        &self,
        query_vector: Vec<f32>,
        popularity_weight: f32,
        recency_weight: f32,
        limit: u64,
    ) -> Result<Vec<ScoredPoint>> {
        let formula = FormulaBuilder::new(Expression::sum_with([
            Expression::score(),
            Expression::mult_with([
                Expression::constant(popularity_weight),
                Expression::variable("popularity"),
            ]),
            Expression::mult_with([
                Expression::constant(recency_weight),
                Expression::variable("recency"),
            ]),
        ]))
        .add_default("popularity", 0.0)
        .add_default("recency", 0.0);

        let response = self.client
            .query(
                QueryPointsBuilder::new(COLLECTION_NAME)
                    .add_prefetch(
                        PrefetchQueryBuilder::default()
                            .query(query_vector)
                            .using(DENSE_VECTOR)
                            .limit(PREFETCH_LIMIT),
                    )
                    .query(formula)
                    .limit(limit)
                    .with_payload(true),
            )
            .await?;

        Ok(response.result)
    }

Reading it top to bottom: prefetch grabs the 100 semantically closest products; the formula then re-scores that pool as score + popularity_weight × popularity + recency_weight × recency; .add_default(...) covers products missing one of those payload fields, so the query never errors on incomplete data.

Shaping results into a Product

A ScoredPoint is a fairly raw, generic Qdrant type. We want something with named fields our own code can work with.

src/qdrant_store.rs
#[derive(Debug, Clone, Default)]
pub struct Product {
    pub id: String,
    pub name: String,
    pub product_type: String,
    pub colour: String,
    pub detail_desc: String,
    pub score: f32,
    pub popularity: f64,
    pub recency: f64,
    pub raw_similarity: Option<f32>,
}

raw_similarity is worth a note: Qdrant only ever hands us the final boosted score. If we want to show the user "here's how close a match this was before we nudged it for popularity," we have to reconstruct it ourselves, by rearranging the same formula:

the same formula, solved for the unknown
score           = raw_similarity + w1*popularity + w2*recency
raw_similarity  = score - w1*popularity - w2*recency
src/qdrant_store.rs
impl Product {
    pub fn from_boosted(point: &ScoredPoint, popularity_weight: f32, recency_weight: f32) -> Self {
        let mut product = Product::from(point);
        let raw = product.score
            - popularity_weight * product.popularity as f32
            - recency_weight * product.recency as f32;
        product.raw_similarity = Some(raw);
        product
    }
}

That leans on a plain From<&ScoredPoint> conversion, which reads the payload fields out of Qdrant's generic key-value map:

src/qdrant_store.rs
impl From<&ScoredPoint> for Product {
    fn from(point: &ScoredPoint) -> Self {
        let payload = &point.payload;
        Product {
            id: point_id_key(point).unwrap_or_else(|| "?".into()),
            name: payload_str(payload, "prod_name")
                .or_else(|| payload_str(payload, "name"))
                .unwrap_or_default(),
            product_type: payload_str(payload, "product_type").unwrap_or_default(),
            colour: payload_str(payload, "colour").unwrap_or_default(),
            detail_desc: payload_str(payload, "detail_desc").unwrap_or_default(),
            score: point.score,
            popularity: payload_f64(payload, "popularity").unwrap_or(0.0),
            recency: payload_f64(payload, "recency").unwrap_or(0.0),
            raw_similarity: None,
        }
    }
}

Turning an opaque point ID into a plain string

A Qdrant point's ID can be either a number or a UUID, wrapped in a few layers of Option. This helper unwraps it safely, without ever taking ownership away from the ScoredPoint we were only lent:

src/qdrant_store.rs
fn point_id_key(point: &ScoredPoint) -> Option<String> {
    let options = point.id.as_ref()?.point_id_options.as_ref()?;
    Some(match options {
        PointIdOptions::Num(n) => n.to_string(),
        PointIdOptions::Uuid(u) => u.clone(),
    })
}
rust concept — .as_ref() and the AsRef trait

This function only borrows point (&ScoredPoint) — it doesn't own it, and it's not allowed to move anything out of it. But point.id is an Option<PointId>, and writing point.id? would try to move the PointId out of a struct we only borrowed, which the compiler won't allow.

Option::as_ref(&self) -> Option<&T> solves exactly this: it converts an &Option<T> into an Option<&T> — same Some/None shape, but now holding a reference instead of the value itself. Nothing gets moved, so the borrow checker is satisfied, and the ? operator can still short-circuit to None if either layer is empty.

This method exists because of a more general pattern in Rust: many types implement the AsRef<T> trait, which just means "I can hand you a cheap reference to a T without giving up ownership of myself." String implements AsRef<str>, Vec<T> implements AsRef<[T]>, and so on. It's the same idea you'll see in function signatures like fn greet(name: impl AsRef<str>), which accept both a String and a &str — the caller doesn't need to know or care which one you actually stored. Option::as_ref() is that same "give me a reference, not the value" idea, specialized to work with Option.

Two more small helpers pull typed values out of Qdrant's generic payload map, and we're done with this file's core logic:

src/qdrant_store.rs
fn payload_str(payload: &HashMap<String, Value>, key: &str) -> Option<String> {
    match payload.get(key)?.kind.as_ref()? {
        Kind::StringValue(s) => Some(s.clone()),
        _ => None,
    }
}

fn payload_f64(payload: &HashMap<String, Value>, key: &str) -> Option<f64> {
    match payload.get(key)?.kind.as_ref()? {
        Kind::DoubleValue(v) => Some(*v),
        Kind::IntegerValue(v) => Some(*v as f64),
        _ => None,
    }
}

5 Handing results to an LLM

Retrieval alone gives you a ranked table. To let someone ask "which of these would work for a wedding?" and get a real sentence back, we pass the retrieved products into a local LLM's prompt as grounding context — the "RAG" in retrieval-augmented generation. We use the rig crate to talk to a local Ollama server, so nothing leaves your machine and no API key is needed.

Rendering products into a context block

src/rag.rs
use crate::qdrant_store::Product;

pub fn build_context(products: &[Product]) -> String {
    let mut context = String::new();

    for (i, p) in products.iter().enumerate() {
        context.push_str(&format!(
            "{}. {} | type: {} | colour: {} | popularity: {:.2} | recency: {:.2}\n",
            i + 1, p.name, p.product_type, p.colour, p.popularity, p.recency,
        ));
        if !p.detail_desc.is_empty() {
            context.push_str(&format!("   description: {}\n", p.detail_desc));
        }
    }
    context
}

Plain text, not JSON — small models follow a short, human-readable list more reliably than they parse structured data, and it keeps the prompt compact.

Asking the question

src/rag.rs
use anyhow::Result;
use rig::client::Nothing;
use rig::prelude::*;
use rig::providers::ollama;

pub async fn answer_with_context(model: &str, question: &str, context: &str) -> Result<String> {
    let client = ollama::Client::new(Nothing)?;

    let preamble = format!(
        "You are a helpful shopping assistant. Answer using ONLY \
         the product listings below. If they don't contain a good \
         answer, say so instead of making one up.\n\nPRODUCTS:\n{context}"
    );

    let agent = client.agent(model).preamble(&preamble).build();
    let response = agent.prompt(question).await?;

    Ok(format!("{response}"))
}

Nothing is Rig's way of saying "this provider needs no API key" — appropriate for a local Ollama server. The instruction to answer only from the listed products matters more than it looks: it's what keeps a small local model from confidently inventing a product that was never retrieved.

6 Wiring it together in main.rs

Everything above is a building block. main.rs is the CLI that decides what arguments to accept and in what order to call the blocks.

The arguments

src/main.rs
use clap::Parser;

#[derive(Parser, Debug)]
#[command(author, version, about)]
struct Args {
    /// The search / question text
    query: String,

    #[arg(long, default_value_t = 0.05)]
    popularity_weight: f32,

    #[arg(long, default_value_t = 0.05)]
    recency_weight: f32,

    #[arg(long, default_value_t = 10)]
    limit: u64,

    #[arg(long, default_value = "http://localhost:6334")]
    qdrant_url: String,

    #[arg(long, default_value = "granite4.1:3b")]
    model: String,

    #[arg(long, default_value_t = false)]
    no_llm: bool,
}

clap's derive macro turns this struct into a full --help-documented CLI just from its field types and attributes — no argument-parsing code to write by hand.

The pipeline

src/main.rs
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let args = Args::parse();

    // 1. embed the query
    let embedder = Embedder::new()?;
    let query_vector = embedder.embed_query(&args.query)?;

    // 2. boosted search against Qdrant
    let store = Store::connect(&args.qdrant_url)?;
    let points = store.boosted_search(
        query_vector, args.popularity_weight, args.recency_weight, args.limit,
    ).await?;

    let products: Vec<Product> = points.iter()
        .map(|p| Product::from_boosted(p, args.popularity_weight, args.recency_weight))
        .collect();
    print_results(&products);

    if args.no_llm {
        return Ok(());
    }

    // 3. hand the results to the LLM
    let context = rag::build_context(&products);
    let answer = rag::answer_with_context(&args.model, &args.query, &context).await?;
    println!("\n🤖 Answer:\n{answer}");

    Ok(())
}

Notice the shape: each numbered step only depends on the step before it, and each one is a single call into a module we already finished and — separately — already understand. That's the payoff of splitting the file in the first place.

why #[tokio::main]?

Both the Qdrant client and Rig's Ollama client use async functions under the hood — they can pause while waiting on the network instead of blocking a whole thread. Rust doesn't ship a built-in way to actually run async code; tokio is the runtime that does it, and the #[tokio::main] macro is what lets an ordinary-looking async fn main() act as your program's entry point.

What you actually built

  • An embedding wrapper that turns a query into a vector in the same space as your indexed data.
  • A Qdrant client that prefetches semantic candidates and re-ranks them server-side with a formula query.
  • A conversion layer (From<&ScoredPoint>) that turns a generic database result into a typed struct your own code can reason about.
  • A RAG step that grounds a local LLM's answer in exactly the products you retrieved — nothing more.
  • Along the way: Vec::remove for taking ownership out of a collection, and Option::as_ref() / the AsRef trait for borrowing instead of moving.

From here, natural next steps are a compare_search mode that shows how much the boost actually moved each result (semantic rank vs. boosted rank), or swapping the fixed weights for ones tuned against real click data.
